## 1. 背景与目标

合流预算已算出：视觉基底 `bit2_final` **4717/4900 MSlice（余 183）**；音频侧新增 **525~636 MSlice**；合流 **5242~5353**；整板目标 4850 ⇒ **仍需回收约 600 MSlice**。

执行方在该报告第 3 条已如实声明：`updater 4614 LE / renderer 2248 LE / label_store 1366 LE` **"只是定位大头，没有确认其可回收额度"**。

**本轮任务就是把这句话变成一张账。**

## 2. 交付物

**一张表**（建议同时给 Markdown + JSON），每行一个候选回收点：

| 列 | 要求 |
|---|---|
| 模块 / 实例路径 | 门级层次名，可追溯到具体 `.v` 与行 |
| 当前 LE（并给出 MSlice 折算） | **必须给依据来源**（门级 `*.area` / 层级报告路径 + 该行的原始数字） |
| 候选回收手段 | 具体到做法（如"移位替代乘法""ROM 展开替代查表""共享实例""位宽裁剪"） |
| 预计回收量（区间） | 给上下界，**不得只给单点值** |
| **依据等级** | 标注是「已有门级实测」/「模块级探针」/「纯设计估算」——三者必须分开，不得混计 |
| 对功能的影响 | 是否改变黄金输出 / 是否改变时序契约 |
| 对资源池的影响 | 涉及 9K / 32K / DSP 的另列 |
| 风险 | 时序、CDC、布局敏感（LESSON-020/021）等 |

**末尾必须有**：合计回收量的**下限与上限**，以及**能否填平 600** 的明确结论（能 / 不能 / 需要叠加哪些条件）。

## 3. 冻结项（**不得列入回收手段**）

以下为已裁定冻结或不可删，**清单里若把它们列为回收来源，本轮直接判不合规**：

- **PCB 线稿 / W2 更新器 / S2 渲染器 / 底部 128 路柱形图**（主人 2026-09-27 裁定：全部效果冻结不可砍）
- **官方 I2S / ACR**、**CRC 后提交保护**、**epoch / seq / first_sample** 语义、**错误静音**
- 已上板验收的 SPI/SD 驱动与 SDRAM 引擎功能正文

## 4. 已知的合理候选（可作起点，但需自行核实额度）

1. **`fat32_file_streamer.v` 第 75/139 行簇号 × SPC 两处乘法** —— 043 侧门级实测该 FAT 子树**占 4 DSP**。改「移位 + 校验 SPC 为二的幂」。
   ⚠️ **注意口径**：这是**已经计在 043 主线账上的**，若合流复用 043 主线树，**不得在本表里二次计账**；若合流是独立树，则需说明。
2. 标签图加载链（已窄化为受控 LBA 直读）是否还有余量。
3. W2 / S2 的**非效果性**部分（如握手簿记、调试端口、未消费逻辑）——只允许触及与画面无关的面。

## 5. 纪律要求

1. **只出账、不动手**：本轮**不得修改任何 RTL**、**不得跑综合或布局布线**、**不得出新 bit**、**不得预记任何节省**；
2. **估算不得冒充实测**：纯设计估算的条目必须显式标注，不得与门级实测混在一起求和；
3. **不得跨工作区改源**：需要改冻结的 W2/S2 实现时，**先报再议**，不得为了凑 600 直接改；
4. **结论要能证伪**：若合计回收量填不平 600，**照实写"填不平"**，并给出还差多少——这比凑数有用得多。

## 6. 回答的问题

本轮必须明确回答一个问题：

> **在不删任何冻结效果的前提下，M6 合流的 ~600 MSlice 缺口，能否回收？**
> - **能** ⇒ 给出回收清单 + 合计下限/上限 + 建议执行顺序；
> - **不能** ⇒ 给出差额，并说明还差的那部分**只有靠什么结构性变化才可能解决**（供主人决策）。
